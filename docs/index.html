Why it existsNega kerak

Deploy logic keeps getting gitignored Deploy mantig’i doim git’dan tashqarida qoladi

Release scripts usually sit in the same directory as the .p8 key and the service-account JSON. So the whole directory gets gitignored — and the logic quietly stops being version controlled. It survives until the day someone clears that folder. Release skriptlari odatda .p8 kaliti va service-account JSON bilan bir papkada turadi. Shuning uchun butun papka gitignore qilinadi — va mantiq jimgina versiya nazoratidan chiqib ketadi. U kimdir o’sha papkani tozalaguncha yashaydi.

deploykit splits the three things that get tangled together: deploykit bir-biriga chalkashib ketadigan uch narsani ajratadi:

Five verbs, one config Besh buyruq, bitta config

init Write deploy.yaml, .env.example and .last_build_number deploy.yaml, .env.example va .last_build_number yaratadi
doctor Check every precondition and report all of them, not just the first Barcha shartlarni tekshiradi va birinchisini emas, hammasini ko’rsatadi
build Build the artifacts and record what was made, for which environment Artefaktlarni quradi va nima, qaysi muhit uchun qurilganini yozib qo’yadi
upload Upload the last build. Safe to retry — it never bumps the build number Oxirgi build’ni yuklaydi. Qayta urinish xavfsiz — build raqamini oshirmaydi
publish build + upload + notify build + upload + xabarnoma

All of them except init take --dev, --release or --env <name>, plus --android / --ios. A --dry-run is a real check: it loads the config, resolves every ${VAR} and runs pre-flight. It fails if your key is missing. It just does not build or upload anything. initdan tashqari hammasi --dev, --release yoki --env <nom> qabul qiladi, hamda --android / --ios. --dry-run haqiqiy tekshiruv: config o’qiladi, har bir ${VAR} almashtiriladi va oldindan tekshiruv bajariladi. Kalit yo’q bo’lsa yiqiladi. Faqat hech nima qurmaydi va yuklamaydi.

ConfigurationSozlama

Secrets never enter the file Maxfiy qiymatlar faylga tushmaydi 

version: 1

app:
  root: .
  android_package: com.example.app

environments:
  dev:
    branch: '^versions/.+/dev$'      # regex; omit the field to disable
    dart_defines:
      PROD_URL: 'false'
      INSPECTOR: 'true'
    android:
      artifacts: [aab, apk]
      apk:
        split_per_abi: true
        target_platform: android-arm64
      play:
        track: internal
        status: completed
    ios:
      testflight_internal_only: true
    notify:
      telegram:
        message: 'DEV build, test only'
        attach: apk
        on_oversize: zip          # zip | fail | skip

  release:
    branch: '^versions/.+/release$'
    dart_defines: {}                 # empty on purpose — see below
    android:
      artifacts: [aab]
      play:
        track: production
        status: draft

integrations:
  play:
    service_account: ${PLAY_SERVICE_ACCOUNT}
  app_store:
    key_id: ${ASC_KEY_ID}
    issuer_id: ${ASC_ISSUER_ID}
    private_key: ${ASC_PRIVATE_KEY}
    team_id: ${ASC_TEAM_ID}
  telegram:
    bot_token: ${TELEGRAM_BOT_TOKEN}
    chat_id: ${TELEGRAM_CHAT_ID}

dart_defines: {} is a real value, not “unconfigured”. The defaultValue of each fromEnvironment in your Dart code is normally already the production value, so a production build should pass no --dart-define at all. Writing PROD_URL: 'true' would work, but it hides the intent. dart_defines: {} haqiqiy qiymat, “sozlanmagan” degani emas. Dart kodingizdagi har bir fromEnvironmentning defaultValuesi odatda allaqachon production qiymati, shuning uchun production build hech qanday --dart-define uzatmasligi kerak. PROD_URL: 'true' yozish ishlaydi, lekin niyatni yashiradi.

branch: '' is an error, not “disabled”. Remove the field to disable the check. An empty string is almost always an accident, and reading it as “disabled” would leave production unguarded. branch: '' — bu xato, “o’chirilgan” degani emas. Tekshiruvni o’chirish uchun maydonni butunlay olib tashlang. Bo’sh qiymat deyarli har doim tasodif, va uni “o’chirilgan” deb o’qish production’ni himoyasiz qoldiradi.

Use block style for ${VAR}. In flow style, {service_account: ${SA}}, YAML reads the { of ${SA} as a nested mapping and fails to parse. ${VAR} uchun block uslubini ishlating. Flow uslubida, {service_account: ${SA}}, YAML ${SA}ning { belgisini ichma-ich mapping deb o’qiydi va parse qila olmaydi.

What it catchesNimani ushlaydi

Failures that otherwise pass quietly Aks holda jimgina o’tib ketadigan nosozliklar

Every one of these succeeds at the step where it goes wrong, and only surfaces much later. Bularning har biri xato sodir bo’lgan bosqichda muvaffaqiyatli tugaydi va ancha keyin bilinadi.

error 91169

Dart code assets install into one shared directory. Run the app on the simulator, then build a release IPA, and Flutter can skip the device install as “up to date” — leaving a simulator framework for Xcode to embed. The build succeeds. App Store Connect rejects the upload after you have already sent 40MB. deploykit purges that cache before every iOS build. Dart code-asset’lari bitta umumiy katalogga o’rnatiladi. Ilovani simulyatorda ishga tushirib, keyin release IPA qursangiz, Flutter qurilma uchun o’rnatishni “allaqachon bajarilgan” deb o’tkazib yuboradi — Xcode esa simulyator framework’ini joylaydi. Build o’tadi. App Store Connect esa 40MB yuklangandan keyin rad etadi. deploykit bu keshni har bir iOS build’idan oldin tozalaydi.

simulator slices

Before uploading, every Mach-O binary in the bundle is read for its LC_BUILD_VERSION. Anything targeting a simulator is caught in seconds — not minutes into an upload that was always going to be rejected. Yuklashdan oldin bundle ichidagi har bir Mach-O faylning LC_BUILD_VERSION qiymati o’qiladi. Simulyatorga mo’ljallangani bir necha soniyada topiladi — baribir rad etiladigan yuklashga daqiqalar sarflamay.

HTTP 413 · ok:false

Telegram reports real success only in the JSON body. curl exits 0 even on a 413, which is exactly how a rejected upload goes unnoticed in a shell script. deploykit reads the ok field and fails loudly. Telegram haqiqiy muvaffaqiyatni faqat JSON javobida bildiradi. curl 413’da ham 0 qaytaradi — aynan shu sababdan rad etilgan yuklash skriptlarda sezilmay qoladi. deploykit ok maydonini o’qiydi va baland ovozda yiqiladi.

versionCode reuse

The build number is bumped before the build, so a failed build skips a number instead of reusing one — Play rejects a duplicate outright. upload never bumps it, which is what makes retrying a failed upload safe. Build raqami build’dan oldin oshiriladi — build yiqilsa raqam o’tkazib yuboriladi, qayta ishlatilmaydi (Play takrorlanganini darhol rad etadi). upload uni hech qachon oshirmaydi, shuning uchun yiqilgan yuklashni qayta urinish xavfsiz.

stored, not deflated

Native libraries inside an APK are stored uncompressed so Android can mmap them straight out of the archive, so an outer zip often helps a great deal. The saving is never assumed: the zip is created, measured, and rejected if it is still over the limit. APK ichidagi native kutubxonalar siqilmagan holda saqlanadi — Android ularni arxivdan to’g’ridan-to’g’ri mmap qiladi — shuning uchun tashqi zip ko’p yordam beradi. Lekin foyda taxmin qilinmaydi: zip yaratiladi, o’lchanadi, va hali ham chegaradan katta bo’lsa rad etiladi.

Four commands to a dry run To’rt buyruqda dry run

in your Flutter project Flutter loyihangiz ichida 
$ deploykit init
  writes deploy.yaml, .env.example, .last_build_number
  and adds .env + .deploykit/ to your .gitignore

$ cp .env.example .env          # then fill in the values

$ deploykit doctor --dev
✓ flutter — available
✓ branch — main — matches
✓ App Store .p8 key — 241 bytes
✗ Play API — key rejected (HTTP 401)

$ deploykit publish --dev --dry-run

Run against a dev environment first. doctor and --dry-run cost seconds; a broken production release costs a review cycle. Avval dev muhitida sinab ko’ring. doctor va --dry-run bir necha soniya oladi; buzilgan production release esa butun ko’rib chiqish siklini oladi.
